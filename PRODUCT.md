# Product

## Register

brand

## Users

TypeScript developers and agent-platform teams who need to connect external
agents to chat, code, issue-tracking, and scheduled work without adopting a
mandatory SaaS control plane. They evaluate OpenMatter through its SDK,
documentation, examples, architecture diagrams, and integration contracts.

## Product Purpose

OpenMatter is the durable Agent Loop framework for work systems. It normalizes
work-platform events and operations, constructs authorized context, preserves
Scope and WorkThread continuity, and connects replaceable Agent runtimes while
leaving reasoning to the Agent and application policy to the user.

The brand should make a sophisticated systems abstraction feel concrete,
inspectable, and trustworthy. Success means a developer can understand the
boundary quickly and believes the implementation will remain portable,
composable, and operationally correct.

## Brand Personality

Precise, material, and quietly opinionated. OpenMatter should feel like an
engineered pigment, a protocol drawing, or a well-made technical manual: strong
enough to be recognizable, restrained enough to support dense information.

## Anti-references

- Generic AI SaaS marketing with electric gradients, glowing purple-blue
  surfaces, glass panels, and interchangeable rounded cards.
- Corporate status green, default Tailwind blue, or an accent sprayed across
  every interactive surface.
- Over-personified Agent branding that confuses a visible bot, a work profile,
  and an execution identity.
- Fashion-editorial styling applied as decoration to technical documentation.
- A dark theme that invents a different brand palette instead of preserving the
  same identity and hierarchy.

## Design Principles

1. **Make the boundary visible.** Diagrams, examples, and labels should reveal
   where work context, Agent reasoning, credentials, and durable state live.
2. **Treat the brand as a material.** Use one saturated blue deliberately and
   let neutral surfaces, typography, and exact spacing carry the system.
3. **Prefer durable clarity over launch-day novelty.** Visual decisions should
   survive long documentation pages, code samples, dashboards, and diagrams.
4. **Keep identities distinct.** Visible authorship, AgentProfile behavior, and
   ExecutionIdentity permissions must never collapse into one visual concept.
5. **Be deployment-neutral in appearance and substance.** Do not make one
   runtime, platform, cloud, or control plane look mandatory.

## Accessibility & Inclusion

Target WCAG 2.2 AA for text, controls, focus states, and semantic status use.
Never encode state with color alone. Respect reduced-motion preferences, retain
keyboard-visible focus, and keep documentation readable under light, dark, and
high-contrast user settings.
