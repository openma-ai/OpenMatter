## 为什么决定要放在 agent 外面

长期跟用户一起干活的 agent，至少要定四件事。现有产品和 dsh 团队的 Super-agent
文章，差别主要落在怎么定它们：

1. **新事件归哪条工作线、哪个 session**，要不要由 coordinator 再往下派。合得多上下文连续但容易排队；分得多能并发，结果又不通气。
2. **事件来了要不要叫醒 agent**，还是只记下来。没人 @ 的群消息、CI、定时触发，主动到什么程度看这条。
3. **人中途改主意时，新消息怎么进正在跑的一轮。**
4. **结果怎么回到用户**，让用户眼里始终像同一个 agent。

OpenMatter 的做法：

- 前两件由应用写成 **Loop**（和 agent 内部的 ReAct Loop 不是一回事；这里的工作线是「哪些事件共用一个 session」，和 dsh 文中偏事件流的 Thread 也不完全一样）。
- 后两件由协议给出默认，应用可改：新消息默认开新 **Turn** 排在当前轮后面；**steer** 打进正在跑的 Turn 是可选扩展，前提是 driver 声明 `capabilities.steering` 并实现 `AgentDriver.steer`。
- 回复是 Turn 里的操作：发送前做新鲜度检查，发送后留回执。

Loop 和回复/steer 协议在 agent 外面，所以同一套编排可以通过 **AgentDriver** 接到 ACP、托管 runtime、进程内 SDK 或自定义 agent。这就是「任意 harness」：换 driver，Loop 还在。

## 核心名词

| 名词 | 作用 |
| --- | --- |
| **Loop** | 应用声明订阅、路由到 WorkThread/Session，以及事件是开工还是只记录。 |
| **Bond** | 工作平台身份 + `SecretRef`；密钥值由 `CredentialResolver` 取。 |
| **AgentDriver** | OpenMatter Session/Turn 到具体 harness 的可替换桥。 |
| **Turn** | Session 里的一次调用；人类新消息默认开新 Turn。 |
| **steer** | driver 支持时，把新话注入正在跑的 Turn。 |
| **coordinator / worker** | `@openma/matter-project-host` 的 Project：coordinator 派活、改方向、取消 worker。 |

`@openma/matter-orchestration` 内置 `claudeTag()`、`linearLoop()`、`coordinatorLoop()`，差别主要在有没有 coordinator、session 怎么分。可与 Claude Tag、Linear Agent Session、Claude Projects 对照理解，并不宣称 OpenMatter 是这些产品的复制品。
